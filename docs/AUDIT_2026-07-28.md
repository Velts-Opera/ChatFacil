   - adicionados triggers equivalentes para conversa/contato/canal;

6. **Painel de administrador**

10. **Consistência de conversa**
    - criado índice único parcial para impedir mais de uma conversa ativa para o mesmo contato/canal/tenant.

11. **Performance**
    - adicionados índices de FKs usados por mensagens, conversas, intakes, matters, documentos, handoffs, filas, agenda e auditoria;
    - políticas duplicadas de empresa foram consolidadas;

## Testes executados

### 1. WhatsApp real — E2E

Executado em produção antes do último hardening do webhook, usando o canal oficial existente.

Resultado observado:

- inbound recebido;
- contato/conversa persistidos;
- `ai_interactions` criado;
- IA gerou resposta;
- envio pela Meta retornou ID de mensagem;
- status posterior `delivered` recebido pelo webhook.

Resultado: **APROVADO**.

### 2. Assinatura do webhook

Depois do hardening:

- POST sem `x-hub-signature-256`: `403`;
- GET de verificação com token incorreto: `403`;
- GET com token realmente salvo no canal: `200` e challenge correto.

Resultado: **APROVADO**.

### 3. Coexistence / handoff sintético assinado

Evento sintético foi assinado no servidor usando o App Secret real, sem expor o segredo.

Sequência:

1. `smb_message_echoes` simulando resposta humana do WhatsApp Business;
2. mensagem inbound posterior do mesmo contato.

Banco confirmou:

- mensagem `human_app` criada;
- `human_handling = true`;
- `ai_handling = false`;
- `ai_paused_until` preenchido;
- inbound posterior registrado;
- `ai_interactions = 0` para esse inbound;
- evento `ai_reply_skipped_human_takeover` registrado.

Dados sintéticos foram removidos após o teste.

Resultado: **APROVADO para a lógica do backend**.

### 4. Auth / senha / RLS sintético

Foram criados dois usuários temporários com senhas aleatórias fortes e confirmação de e-mail apenas para o teste. Após os testes, ambos foram removidos.

Validado:

- senha correta autentica;
- senha incorreta é rejeitada;
- tenants provisionados são distintos;
- usuário enxerga somente sua empresa;
- perfil de outro tenant não é retornado;
- troca de `company_id` é bloqueada;
- criação direta de outra empresa é bloqueada;
- usuário comum não executa `admin_create_company`;
- usuário comum não executa `admin_enter_company`;
- overview de admin não retorna dados para usuário comum;
- `channel_secrets` não é legível pelo cliente;
- contato de tenant A não aparece para tenant B;
- tenant desativado perde acesso ao banco;
- tenant desativado perde acesso às Edge Functions protegidas pelo `requireUser` endurecido.

Resultado: **APROVADO**.

### 5. Superadmin sintético

Usuário temporário foi promovido a `platform_admin`, autenticado via senha e usado contra RPCs reais.

Validado:

- `admin_create_company`;
- empresa aparece no `admin_company_overview`;
- defaults do tenant são provisionados;
- agente/base inicial existem;
- `admin_enter_company` muda o contexto do perfil.

A migration de asserção só foi aplicada após retorno `ok=true` do teste. Dados temporários foram limpos.

Resultado: **APROVADO**.

### 6. Consistência multitenant dos dados atuais

Antes de instalar os triggers de consistência foram consultadas divergências entre:

- mensagem ↔ conversa;
- mensagem ↔ contato;
- mensagem ↔ canal;
- conversa ↔ contato;
- conversa ↔ canal.

Nenhuma divergência existente foi encontrada.

Resultado: **APROVADO**.
